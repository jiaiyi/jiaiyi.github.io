`.docx` 本质是个 zip，里面是 OOXML。用 Python 解析它不难，难的是**你不知道文档里
信息到底是怎么存的** —— 按直觉写的代码往往「不报错，但结果全错」。

而且这些错误的症状通常**出现在下游**（切分、检索、显示），离解析这一步很远，
排查起来很绕。

下面这些都是踩过才知道的。

<!--more-->

## 一、标题层级不在样式名里

第一反应一般是按样式名匹配：

```python
if "标题" in style_name:
    level = int(style_name[-1])
```

这在用默认样式的文档上能用。但遇到**自定义样式**的文档，会一个标题都找不到：

- 样式名是中文自定义的：`一级标题`、`半括号标题（五级）`
- 样式 ID 是乱码：`afc`、`a1`、`HTML1`

真正可靠的是 `styles.xml` 里样式定义上的 **`w:outlineLvl`**（0 起算，`0` = 一级）。

```xml
<w:style w:styleId="afc">                     <!-- styleId 是【属性】→ 用 .get() -->
  <w:name w:val="一级标题"/>                   <!-- 名字跟层级无关，别用它判断 -->
  <w:pPr><w:outlineLvl w:val="0"/></w:pPr>    <!-- 子元素 → 用 .find() -->
</w:style>
```

两个必须处理的细节：

1. **沿 `basedOn` 链回溯。** 很多子样式自己不写 `outlineLvl`，靠继承父样式。
   回溯时要带**深度上限**，否则样式互相引用会成环、直接死循环。
2. **段落级覆盖优先。** 段落自己的 `w:pPr` 里也可能直接写 `w:outlineLvl`，
   优先级高于样式继承。

## 二、代码块按样式名判定会全军覆没

我实测过一份课程讲义：**所有代码段落的 `pStyle` 都是空的**，唯一的特征是字体 `Consolas`。

只按样式名判断 → 代码块数 = 0 → 接下来就是第三节那场灾难。

**判定要用两路「或」**：

```python
def is_code_paragraph(p, style_name, is_heading=False):
    # 第一路：样式名（对规范文档有效）
    if any(k in (style_name or "").lower() for k in ("preformatted", "code", "代码")):
        return True

    # 标题不参与字体判定，防止把标题误判成代码
    if is_heading:
        return False

    # 第二路：字体
    for rf in p.iter(R_FONTS):                      # rFonts 是子元素
        for attr in ("ascii", "hAnsi", "cs", "eastAsia"):   # 四个都要查！
            font = (rf.get(W + attr) or "").lower()
            if font and any(m in font for m in MONOSPACE):  # consolas / courier / monaco ...
                return True
    return False
```

两个容易漏的点：

- **`rFonts` 有四个属性**：`ascii`（西文）、`hAnsi`（中文）、`cs`、`eastAsia`。
  **Word 通常只写其中一个** —— 只查一个必然漏判。这四个都得看。
- **连续代码段落要合并成一个围栏。** 否则一行一个 ` ``` `，Markdown 直接废掉。

## 三、连锁灾难：Python 注释变成了 Markdown 标题

这是最隐蔽的一环。

围栏没包住代码时，代码里的 Python 注释（`# 创建引擎`）会原样落进 Markdown。
而它在文本上和 Markdown 标题**完全无法区分**。

下游如果按 `^#{1,6}\s+.+` 切分章节，后果是：

- 每条注释变成一个「章节标题」
- 标题栈被污染 → `chapter` / `parent` 字段里变成代码片段
- 章节层级被切碎
- 最终答案的「参考来源」里，显示的是代码当章节名

修复前后的实测对比（同一份代码密集的讲义）：

| | 修复前 | 修复后 |
|---|---|---|
| 围栏代码块 | 0 | 50 |
| 初切 sections | 239 | 116 |
| `chapter` 被代码污染 | 大量 | 0 |

**怎么排查**：数一数 `md` 里以 `#` 开头的行数，再数「不在围栏内的」有多少 ——
两者的差额就是被围栏保护住的注释数。差额为 0 就说明围栏根本没生效。

⚠️ 判断「行是否在围栏内」必须**逐行遍历状态机**，别用 `md.count("```")` ——
代码内容里本身也可能含 ` ``` `，计数会错。

## 四、图片有两种写法，都要认

| 版本 | 路径 | 图片 id 位置 |
|---|---|---|
| 新版 | `w:drawing` → `a:blip` | `r:embed` |
| 老版 | `w:pict` → `v:imagedata` | `r:id` |

拿到 `rId` 后，去 `word/_rels/document.xml.rels` 查 `Target`，
再以 `word/` 为基准解析出真实路径。

两个细节：

- **跳过 `TargetMode="External"` 的关系** —— 那是超链接，不是图片。
- 下游处理不了的格式（比如 `emf`）**照样导出文件，但别写进 Markdown**，
  否则会留一堆打不开的坏链接。

## 五、其它几个必踩的坑

- **`~$xxx.docx` 是 Office 锁文件。** 用户打开文档时生成，它不是 zip，
  解析必然抛 `BadZipFile: File is not a zip file`。
  批量导入脚本必须跳过 `~$` 前缀以及 `.tmp/.bak/.lck`。
  （真实场景：数据目录里恰好有一个，整个批量任务直接崩。）
- **ElementTree 的 tag 带命名空间全名。** 它是 `{http://...}t`，
  不能拿 `"w:t"` 这种带前缀的短名去比 —— **永远不会相等**，然后静默取不到文本。
  同样地，`w:styleId` 是**属性**（用 `.get()`），`w:outlineLvl` 是**子元素**（用 `.find()`）——
  这两个混用是高频笔误。
- **取段落文本要递归。** 用 `iter()` 才能覆盖 `w:hyperlink` 里的 `w:t`；
  `w:tab` / `w:br` 也要单独映射，否则换行全丢。
- **表格转 Markdown 前做三件事**：单元格里的 `|` 转义、列数补齐、
  分隔行必须是 `["---"] * n` —— 写成 `"---" * n` 会得到 `------` 这种在有的渲染器里
  会被当成文本的长横线。
- **⚠️ 公式（OMML）会丢。** 数学文档的公式是 `m:oMath` 对象，不是 `w:t` 文本。
  不专门处理，剩下的就只有「记作、或。」这种残缺句子。数学类语料要单独评估。
- **`#` 后面必须有空格**，否则下游的 `^#{1,6}\s+.+` 匹配不到。

## 六、验收口径：别只看「没报错」

解析完必须打这几项指标，才能判断结果是否可信：

```
md 字符数
围栏代码块数
以 # 开头的行数（要区分围栏内外）
表格行数
图片导出与引用数
```

**代码块数为 0，而文档明明是代码讲义 → 一定是第二节那个问题。**

### 再算一笔账：文件大小 vs 正文长度

讲义类文档经常出现 **文件 3 MB，正文却只有 18 KB** 的情况 —— 差额几乎全是截图
（我那次是 26 张）。

这种情况下，纯文字解析会**静默丢掉大量信息**（操作步骤、界面、配置项全在图里），
而所有指标看起来都正常（标题有、代码块有、表格有），最容易被当成「解析成功」。

所以遇到比值悬殊，一定要**同步导出图片并看几张关键的**。导出时顺手记录每张图的
**上文段落** —— 比按序号猜它在哪一节省事得多。

## 小结

| 你想当然的做法 | 实际应该 |
|---|---|
| 按样式名判标题层级 | 读 `w:outlineLvl`，沿 `basedOn` 链回溯 |
| 按样式名判代码块 | 加一路字体判定，查全 `rFonts` 四个属性 |
| 用 `"w:t"` 比 tag | 用 `{namespace}t` 全名 |
| `md.count("```")` 数围栏 | 逐行状态机遍历 |
| 解析不报错就算成功 | 跑真实文件，一路验到下游切分结果 |

**核心认知：文档里的信息不一定按你期望的方式存储，而错误往往在下游才暴露。**
解析器写得对不对，不看它跑没跑通，看下游拿到的东西对不对。
