RAG 检索路由：为什么「精确问课程名」反而答错

2026-09-28 · 9 分钟读完 RAG检索路由LLM

一个反直觉的实测结果，先说结论：

问法 top1 分数 结果
「有没有讲 Galois 理论的课」 0.7529 ✅ 命中
「有哪些 Python 相关课程」 0.6427 ❌ 0.63~0.64 平坦分布
「X 入门班的章节结构是什么」 0.7978 ❌ 完全错的课

注意第三行：用户已经明确说出对象名了，向量却给出了另一门课，分数还有 0.79。

这是把「按名查」「列列表」「推荐」「文档问答」全都塞进同一条向量链路时会遇到的典型问题 —— 前几类本质是结构化查询，不是语义相似度问题。

一、三条硬经验

从上面这组数据能直接读出三件事：

① 精确问法必须先走结构化。

用户已经说出对象名了，向量却可能给出「语义最像」的另一个对象 —— 而且分数不低。这种情况光靠调阈值是救不了的，因为 0.79 看起来比正确的 0.75 还要「自信」。

② 泛化问法不要迷信语义。

当 top-k 的分数挤在一起（比如全在 0.63~0.64），说明模型根本没把它们区分开。这时候任何阈值都拦不住 —— 你设 0.65 会全过，设 0.7 会全挂。应该走结构化筛选或者回落。

③ 主题词独特的问法，语义很好用。

「Galois 理论」这种专有名词，语义检索能准确命中。这才是语义兜底真正的价值区间 —— 不是拿它当万金油。

二、四层递进 + 回落（可直接套用的骨架）

① 结构化匹配：对象名 / 问题里直接含对象名（n-gram 反向撞名字）
        ↓ 未命中
② 意图词召回：难度/层级/类型词（入门·进阶·就业…）→ 按名称层级词筛候选
        ↓ 未命中
③ 语义兜底：语义召回 + 【分数门槛】
        ↓ 未命中
④ 回落：清空所有收窄条件，交给常规检索链路

① 反向匹配：拿对象名去撞问题

对象总数不大时（几百条），把对象名当字典去撞用户问题，比在库里拼正则可靠得多。

做法：生成问题的 3~8 字 n-gram，看哪一段被对象名包含。完整名出现给最高分，n-gram 越长越可信。

⚠️ 必须维护一份通用词黑名单（课程 / 相关 / 哪些 / 介绍 …），否则这些词会命中一大片，路由直接失效。

③ 语义兜底的两条纪律

纪律一：必须设分数门槛。

实测 0.72 左右是合适的切点 —— 独特主题词能到 0.75+，泛化问法挤在 0.63 附近，门槛正好把两者切开。

低于门槛的，宁可回落，也不拿噪声冒充命中。

纪律二：候选名回表时只做精确匹配，绝不用模糊兜底。

语义召回的候选名里可能混进 课程 这类通用词。一旦走模糊匹配，等于把整库捞出来 —— 更糟的是，它会阻断回落：一个错误的命中占住了位置，后面的兜底逻辑就不会触发。

④ 回落是必须的，不是可选的

同一个语料库里经常有两套分类体系互不相干的数据。我遇到过的情况是：一套是「培训班系列」，另一套是「课程讲义」，讲义里的课程名在系列名里 0 命中。

少了回落，用户问「有哪些 Python 相关课程」会被硬答成「没有」—— 而 Python 其实就在讲义里躺着。

实现要点：回落时必须把之前收窄的过滤条件（比如 content_type == "xxx"）清空再交给下游，否则下游带着收窄条件去查，照样 0 条。

三、路由决策别只依赖 LLM 分类

多层路由通常靠「让 LLM 输出一个 intent 字段」来分流。不要只信它。

实测同一个批次里：

  • 「查询函数相关的选择题」→ 判成 question ✅
  • 「递归相关的多选题」→ 判成 doc_qa ❌ → 直接漏掉题库分支，走向量检索拿到 0 条

两条问法的结构几乎一样，模型却给出不同结果。这类「不稳定」比「一直错」更难发现 —— 因为它在前几个用例上表现完全正常，你很容易以为路由没问题。

对策：找出该意图的强信号词，用规则强行覆盖：

def _override_intent(query, intent):
    if any(term in query for term in STRONG_SIGNAL_TERMS):   # 如题型词：选择题/多选题/判断题
        if intent != TARGET:
            logger.info(f"意图纠正：{intent} → {TARGET}")
        return TARGET
    return intent

三个要点：

  • 强信号要真的强（「选择题」几乎只有一个含义）。弱信号别硬兜，会误伤别的意图。
  • 只做单向纠正 —— 把漏判的补上，不要用它推翻模型判对的结果。
  • 一定要打日志（意图纠正：A → B），否则这类兜底出了问题没人看得见。

一个推论：凡是「路由决定走哪条链路」的地方，都值得问一句 —— 如果这一步判错了，用户看到的是不是「查不到」？ 如果是，就该有规则兜底或者降级路径。

四、把结构化数据接进既有链路：对齐 schema

结构化查询命中的结果，不要另写一条答题链路。

把它转成既有检索链路输出的同一种文档结构（text / source / title / score / 业务字段），答案生成节点就一行都不用改 —— 引用块、来源标注、图片提取全部自动复用。

最省事也最不容易出 bug 的接法：新数据源，旧 schema。

五、落库前先离线诊断

抽取阶段就要输出诊断，别等入库后才发现问题：

  • 总条数、缺失关键字段的条数、唯一键是否重复（它要当 upsert 的幂等键）
  • 子结构完整率（比如「全部模块的名称 / 编码 / 课时字段完整率都是 100%」）
  • 假设验证：如果你根据某个规律做了派生（比如「同组内前一个对象是先修课」）， 把分组统计打出来验证。我那次期望「每组 3 个成员」，实测 73 组 × 3 正好闭环 —— 假设被数据证实，派生字段才敢用
  • 语料里没有的字段要显式标注来源（如 prerequisites_source="derived_from_..."）， 避免把推导值当成原始数据

六、三个常见误判

① 只看召回是否为空，不看召回对不对。

语义检索几乎不会返回空 —— 它总会给你 5 条「很像」的东西。必须人工看 top-1 是否真的正确，否则你会把噪声当命中。

② 用模糊匹配做兜底。

在「回表取详情」这一步用模糊匹配，等于把噪声放大。模糊兜底只适合「用户给的主体名」这种高置信输入，不适合「语义召回出来的候选名」。

③ 以为分数归一化后就可比。

norm_score=True 的分数只在同一次检索内可比，跨问法不可比 —— 上表里 0.64 和 0.75 都是各自那次检索的「top1」。

七、把「跟着语料变」的参数抽成配置

上面提到的那些词表和阈值（通用词黑名单、层级同义词、语义分数门槛、字段标签）全部是跟着语料走的。

写死在逻辑代码里，换一套数据就得改代码 —— 这会让系统变成「只能跑那份 demo」。

做法：集中到一个配置模块，逻辑代码只 import，不含字面量。

  • 字段标签用多别名：("适合人群", "适用人群", "面向人群") —— 换文档不用改代码
  • 分组/推导类规则给「开关 + 深度」参数（如 SERIES_GROUP_PATH_DEPTH = 2，设 0 即关闭）， 别硬编码 parts[:2]
  • 由配置生成正则时，可选分支要按标签长度降序排列 —— 否则短标签会先吃掉长标签 （编码 会匹配掉 模块编码 的前缀，这个 bug 很隐蔽）

判断标准：换一套数据，是否只需要改配置？ 需要改逻辑，就说明耦合没拆干净。

同时要有边界感：不为「某份样例语料里恰好出现或缺失的某个值」做特化兜底。 实例数据里的分类体系冲突、个别字段抽取不准，只要整体能跑就接受 —— 特化兜底反而是负债。

小结

问题 对策
精确问名却召回别的对象 先走结构化匹配，别指望向量
泛化问法分数挤在一起 没有区分度，任何阈值都无效 → 走结构化或回落
唯一有区分度的是专有名词 这才是语义兜底的价值区间
答案硬答「没有」 缺回落（且回落时要清空收窄条件）
LLM 意图分类时对时错 用强信号词做单向纠正 + 打日志
换语料就得改代码 词表和阈值全部抽成配置

核心一句：能用字段查的，就别用向量查；向量只做兜底，且必须有门槛。
